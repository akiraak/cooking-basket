# ユーザーティア × 機能マトリクス — 検討資料

## 目的・背景

現状、お料理バスケットは **未ログイン（ゲスト）** と **ログイン（無料）** の 2 ティアで稼働しており、
ティアの境界自体は実装済み（`docs/plans/archive/no-login-mode.md` 参照）。
一方で **有料プラン** は未定義で、

- 何を有料にすると価値が出るのか
- 無料との差を「ユーザーがどう感じるか」「なぜ課金するか」がぼやけている

ため、機能 × ティアのマトリクスと、ユーザー視点の動機設計を一枚にまとめておきたい。
本ドキュメントは **叩き台**（仮説 + 論点列挙）であり、確定スペックではない。
合意が取れたら `docs/specs/feature-tiers.md` 等に正式化し、課金実装プランを別途切り出す。

---

## 現状サマリ（実装済み）

サーバ実装の事実だけ抜き出すと:

- **AI 系** (`/api/ai/*`): `optionalAuth` + `rateLimitAi`。未ログインでも叩ける
  - 上限はランタイム設定（admin から書換可）。デフォルト 1日あたり **ゲスト 3回 / ログイン 20回**
  - ゲストは `X-Device-Id` ヘッダ必須。サーバで sha256 ハッシュ化して `ai_quota` テーブルに記録
  - 上限超過は 429 `ai_quota_exceeded` + `resetAt`（JST 翌 00:00）
- **買い物リスト / 料理 / レシピ** (`/api/shopping`, `/api/dishes`, `/api/saved-recipes`): `requireAuth`
- **データ移行** (`/api/migrate`): `requireAuth`。未ログイン時にローカル保存していたデータをログイン時にサーバへ同期する用
- **管理画面** (`/api/admin/*`): Cloudflare Access（別系統。本ティア設計の対象外）

モバイルクライアントは Zustand store に `mode: 'local' | 'server'` を持ち、未ログイン時は AsyncStorage、
ログイン後はサーバ API。`migration.ts` がローカル → サーバの一括移行を担当（実装は refactor 8 完了時点）。

つまり **「未ログイン = 端末ローカル + AI 試用 3 回」「ログイン = サーバ同期 + AI 20 回」** が既存の境界。
本ドキュメントが新規に検討するのは **有料プラン** の追加。

## ユーザーストーリー（3 ティアの想定ジャーニー）

```
[App Store で発見] → 起動
   ↓
[ゲスト] 即タブに入る。料理を 1〜2 個追加して AI 提案を試す
   ↓ (3回使い切る or レシピを保存したくなる)
[無料アカウント] メール OTP で登録。ローカルデータをサーバへ移行。AI 20回/日に拡大
   ↓ (20回でも足りない / 高度な機能が欲しい)
[有料プラン] サブスク購入。AI 上限解放 + プレミアム機能
```

**各遷移の動機（仮説）**:

| 遷移 | 主な動機 | 補助動機 |
|------|--------|--------|
| ゲスト → 無料 | レシピを残したい / AI をもっと使いたい / 別端末で見たい | ストアアプリの「ちゃんとしたユーザー」になる安心感 |
| 無料 → 有料 | AI 回数が足りない / 高度な機能（後述）を使いたい | サービスを応援したい |

ゲスト → 無料 の摩擦は既に低い（メール 1 通でいい）。
無料 → 有料 の摩擦は高い（クレカ + ストア課金）ので、**有料に明確な「常用ユーザーの痛み」を解消する機能**を載せる必要がある。

## 機能 × ティア マトリクス

✅ = 利用可、🔒 = 上位ティアで解放、— = 該当なし

| カテゴリ | 機能 | ゲスト | 無料 | 有料（仮） | 備考 |
|---|---|---|---|---|---|
| **買い物リスト** | 食材の追加・編集・チェック・並べ替え | ✅（端末内） | ✅（同期） | ✅ | |
| | 料理単位のグルーピング | ✅ | ✅ | ✅ | |
| | 端末間同期 | — | ✅ | ✅ | 無料の主たる価値 |
| | 家族・共同編集（複数アカウントで 1 つのリスト） | — | 🔒 | ✅ | **有料候補①** |
| **料理 / レシピ** | 料理の登録 | ✅（端末内） | ✅ | ✅ | |
| | AI 具材・レシピ提案 | ✅ 3回/日 | ✅ 20回/日 | 🔒 **無制限 or 100回/日** | **有料候補②**（最有力） |
| | レシピ保存（自分のレシピ） | ✅（端末内） | ✅ | ✅ | |
| | みんなのレシピ閲覧 | ✅ | ✅ | ✅ | 公開データなので全員 |
| | みんなのレシピへ公開 / いいね | — | ✅ | ✅ | サーバ集計が要る |
| **AI 機能の質** | レシピ生成（標準モデル） | ✅ | ✅ | ✅ | |
| | レシピ画像生成 | — | — | 🔒 ✅ | **有料候補③** |
| | 高品質モデル（Pro 系）切替 | — | — | 🔒 ✅ | **有料候補④**（要コスト試算） |
| | 写真から料理名認識（食材棚 → 料理） | — | — | 🔒 ✅ | **有料候補⑤**（プロダクト広がりが大きい） |
| **データ管理** | エクスポート（買い物リスト・レシピを CSV/JSON で書き出し） | — | 🔒 | ✅ | **有料候補⑥**（軽量だが地味に効く） |
| | レシピ生成履歴の長期保持 | — | 直近 N 件 | ✅ 全件 | 候補。ただし現状履歴 UI 未実装 |
| **その他** | 広告 | （現状なし） | （現状なし） | — | 広告は導入予定なし＝差別化軸にしない |
| | サポート優先対応 | — | — | ✅ | 体感価値の補助 |

**マトリクスの読み方の注意**:
- 「無料 → 有料」の差が **質か量か** を意識する
  - 量（AI 回数）だけだと「足りないユーザーだけが課金する」＝ 課金率が伸びにくい
  - 質（画像生成・写真認識）を 1 つ以上載せると「使いたいから課金する」誘因になる
- ゲストの試用枠は「触ってログインしたくなる」最短経路に絞る。機能を増やすほど登録動機が薄くなる

## 有料プランの仮説（暫定）

### プラン A: シンプル単一プラン（推奨初期形）

| 項目 | 内容 |
|---|---|
| 名称（仮） | お料理バスケット プラス |
| 価格（仮） | 月額 ¥480 / 年額 ¥4,800（年額 2 ヶ月分割引） |
| 含まれる機能 | AI 100 回/日 + レシピ画像生成 + 写真認識 + 家族共有（後発） |
| プラットフォーム | iOS: StoreKit / Android: Google Play Billing |
| 体験 | 7 日無料トライアル |

価格は **コスト試算（特に画像生成と Pro モデル）** が固まってから確定。
StoreKit / Play Billing は 15〜30% の手数料があるため、Gemini 実コスト × 想定利用回数 × 安全係数で逆算する必要あり。

### プラン B: 段階プラン（複雑化リスク高）

無料 / ライト（¥240）/ プラス（¥480）の 3 段。
ライトは「AI 50 回/日 + 画像生成なし」など。
管理コストが上がり、初期は推奨しない。**選択肢としてのみ記載。**

### 課金プラットフォームの制約メモ

- iOS の有料機能は **必ず StoreKit を経由**（Web 課金リンクへの誘導は規約違反、2024 年改定で米国では緩和されたが日本は依然 NG）
- Android は Play Billing が主流だが、外部課金も一定許容（ただし運用コスト）
- **サブスク状態のサーバ反映**: StoreKit / Play Billing の Server Notification を受ける webhook が必要 → サーバ実装の重さは中程度
- 復元（Restore Purchases）動線は審査要件

## 「なぜ課金するか」の動機設計

### 🟢 効くと思われる動機（採用候補）

1. **AI 回数の頭打ち** — 平日にレシピを 3 つ作る家庭は容易に 20 回を超える。痛みが日常的
2. **画像生成** — 「どんな料理か想像できる」は購買意欲を直接刺激する。SNS 親和性も高い
3. **写真認識（食材棚 → 料理）** — ゼロから料理名を入力するハードルを下げる。ヘビーユーザーほど価値を感じる
4. **家族共有** — 夫婦・親子で買い物リストを同期したいニーズは普遍的。ただし実装重め

### 🟡 弱い動機（補助に留める）

- データエクスポート（地味、解約時の安心材料）
- サポート優先対応（実コミュニケーション量が見えないので約束しすぎない）
- 履歴の長期保持（履歴 UI が無いと無価値）

### 🔴 採用しないほうが良い動機

- 広告非表示 — 現状広告がないので差別化にならない。今後も広告は入れない方針なら言及不要
- 「全機能解放」訴求 — ユーザーが「無料は機能制限版」と認識すると基本体験への満足度が下がるリスク

## ユーザー視点の文言サンプル（UI コピー検討用）

### ゲスト → 無料 の誘導モーダル（AI 上限到達時）

```
今日の AI 提案 3 回を使い切りました。
無料アカウント登録で、1 日 20 回まで使えます（メール 1 通で完了）。
[ログイン / 登録]   [明日まで待つ]
```

### 無料 → 有料 の誘導（AI 上限到達 or 画像生成タップ時）

```
お料理バスケット プラスで、
✓ AI 提案を 1 日 100 回まで
✓ レシピの完成イメージを画像で確認
✓ 写真から料理名を自動認識
7 日無料トライアル → 月 ¥480
[詳しく見る]   [今は無料のまま]
```

文言上のポイント:
- ゲスト誘導は「登録のハードルが低い」ことを強調（メール 1 通）
- 有料誘導は「3 つの具体的価値」を箇条書きで一目で分からせる
- 「今は〜のまま」のオプションを必ず残す（強制感を出さない）

## 論点・未決事項

着手前に user 判断が必要、もしくはチームで詰める論点。

### 価格・収益モデル

- [ ] 月額／年額の価格レンジ（仮 ¥480 / ¥4,800）の妥当性
- [ ] 無料トライアルの日数（7 / 14 / 30）
- [ ] 単一プラン or 段階プラン
- [ ] iOS/Android で価格差を付けるか（手数料差を価格に転嫁するか）

### 機能の範囲

- [ ] AI 回数解放のラインを「無制限」とするか「100 回/日」とするか（コスト青天井防止）
- [ ] 画像生成・写真認識を **初版に入れるか** 後発でリリースするか
- [ ] 家族共有を有料機能とするか、無料にしてユーザー数で勝負するか
- [ ] エクスポートを有料の差別化に入れるか、無料の安心材料として開放するか

### 実装・運用

- [ ] StoreKit / Play Billing の webhook を受けるサーバ機能の実装規模見積（別プランで詳細化）
- [ ] サブスク状態を `users` テーブルに持たせるか、別テーブル `subscriptions` に切るか（後者推奨）
- [ ] 解約時の挙動: 即時失効 vs 期間末まで利用可 — App Store ガイドライン上は期間末まで可が一般的
- [ ] サブスク状態と AI 上限の紐付け: `rateLimitAi` ミドルウェアに `getEffectiveAiLimit(userId)` を生やして、有料ユーザーは `ai_limit_premium` 設定値を読む構成

### ユーザー体験

- [ ] 有料を解約したら何が消える / 残るか（買い物リストや保存レシピは無料機能なので残る前提）
- [ ] 「お試し」「ファミリー」「学生」割引の有無
- [ ] 何画面で誘導を出すか（AI 上限到達時、レシピ画像 UI タップ時、メニューの "プラスを試す" 等）
- [ ] プライバシーポリシーへの追記（決済情報は Apple/Google が処理し、当社は顧客情報を保持しない旨）
